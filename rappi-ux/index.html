What broke on my
Soy Rappi shifts.

In October 2026 I worked real deliveries in CDMX with the Soy Rappi courier app. I'm an Android engineer, so I kept recording whenever something got in my way. This page is what I found: 16 issues, why I think they happen, and how I would help fix them, from the product decision down to the Kotlin.

When Oct 7–28, 2026
Where CDMX, one Android phone
Evidence 19 screenshots · 15 recordings
Output 16 issues · dark theme proposal
Context

Why I did this, and how

Most UX reviews happen at a desk. These happened on the street, with an order running and a customer waiting. That changes what matters: a two-second delay on a splash screen is a minor annoyance at home, and a real problem at a red light when you need the delivery address.

I want the app to be better for the people who use it every day. Nothing here is meant as a takedown. Every issue comes with a proposal I'd be glad to build.

01

Capture on real shifts

Screenshots and screen recordings taken on my own phone while working, between Oct 7 and Oct 28. No test accounts, no staged flows.

02

Catalogue with timestamps

I sampled each recording at one frame every two seconds and tied every finding to a source and a moment in it. Related findings were grouped into 16 issues.

03

Rate by impact on a rider

Severity is about the courier on the street, not about how ugly something looks. For each issue I wrote what I saw, the impact, a root-cause hypothesis and a fix at three levels.

To be clear: I have no access to Rappi's code, logs or backend. Everything I describe as observed is visible in my captures. Root causes are hypotheses from the outside and would need client logs and network traces to confirm. Several flows were captured once, so I can't speak to how often they happen. Personal data (courier and customer names, addresses, order numbers) is covered with solid boxes or pixelation, and screens with IDs or faces were left out entirely.

ISS-01P0Startup

Stuck on "Verificando actualización" in the middle of a delivery

About 36 seconds into the wait.

What happens

On a cold start the splash shows the logo, a thin progress line and "Verificando actualización", and it never finishes. I waited about 36 seconds, killed the app from Recents, relaunched and got the same splash. The app reached "En camino al cliente" only at about 1:25 into the recording. A delivery was in progress the whole time.

Impact on the courier

Around a minute and a half with no address, no chat and no "Llegué" button, while the ETA clock keeps running. That can mean a late penalty, and it means stopping in traffic to fight with the phone.

Hypothesis

The startup gate blocks navigation until a network call finishes (an in-app update check, or a forced-update and remote-config fetch) and that call has no timeout and no fallback. On a congested connection it hangs. Killing the app doesn't help because the gate runs again on every cold start. The active order is probably not stored locally, so nothing can render before the network answers.

How I'd fix it
High product · UX · process

Never block access to an active order. "Update available" becomes a banner. Only a version the server flags as critical can block, and only when no order is active. Track cold start to first interactive frame, with a separate number for cold starts during an active order.

Medium architecture
  • Persist the active order in Room through an OrderRepository and render from the database first.
  • Run the update and config check in the background with a hard 3 s timeout.
  • Bind setKeepOnScreenCondition to local readiness only.
  • Add breadcrumbs (startup_gate_start, startup_gate_timeout) to Crashlytics or Sentry.
Low Kotlin
class StartupViewModel(
    private val orders: OrderRepository,
    private val updates: UpdateChecker,
) : ViewModel() {
    val ready = MutableStateFlow(false)
    val updateBanner = MutableStateFlow<UpdateInfo?>(null)

    init {
        viewModelScope.launch {
            orders.activeOrderLocal().first()   // Room, no network needed
            ready.value = true
        }
        viewModelScope.launch {
            val info = withTimeoutOrNull(3_000) { runCatching { updates.check() }.getOrNull() }
            when {
                info?.critical == true && orders.activeOrderLocal().first() == null -> navigateToForceUpdate()
                info != null -> updateBanner.value = info
            }
        }
    }
}
// Activity
installSplashScreen().setKeepOnScreenCondition { !vm.ready.value }
ISS-02P1Errors · i18n

A raw backend error, in English, on the queue screen

Three messages at once, none of them telling me what to do.

What happens

In the virtual queue for a restaurant ("Estás avanzando en la fila") a red snackbar stays on screen: "The storekeeper is not trusted from any geo point." At the same time an orange pill says auto-accept was turned on when I joined the queue, and a banner says "Menos pedidos por tu deuda".

Impact on the courier

I couldn't tell if I was in the queue, banned from that point, or supposed to move. That is waiting time with no feedback. "Storekeeper" looks like internal vocabulary for the courier role.

Hypothesis

The server's message field is displayed as is, with no mapping from error code to localized copy. The backend probably checked my position against the hub's geofence and rejected it. That's a legitimate state. It just needs a message I can act on, like "you're outside the pickup zone, move closer".

How I'd fix it
High product · UX · process
  • A copy guide for errors: what happened, why, and what to do next.
  • No raw server text in production builds.
  • A string catalogue owned by product, with an es-MX linter in CI for accents and tone.
  • Geofence errors show the distance and a "Show me where" action.
Medium architecture
  • Errors carry a stable code; the client maps it to a sealed DomainError.
  • Unknown codes fall back to a localized generic message and get logged with the raw payload, which is never shown.
  • Truly dynamic server strings come with a locale and are translated server-side.
Low Kotlin · Compose
sealed interface DomainError {
    data class OutsideGeofence(val meters: Int, val hub: LatLng) : DomainError
    data object Network : DomainError
    data class Unknown(val code: String) : DomainError
}

fun ApiError.toDomain(): DomainError = when (code) {
    "STOREKEEPER_UNTRUSTED_GEO" -> DomainError.OutsideGeofence(meta.distanceM, meta.hub)
    "NETWORK_TIMEOUT" -> DomainError.Network
    else -> DomainError.Unknown(code).also { Telemetry.unmappedError(code, rawMessage) }
}

@Composable
fun DomainError.message(): String = when (this) {
    // "Estás a %d m del punto. Acércate para entrar a la fila."
    is DomainError.OutsideGeofence -> stringResource(R.string.err_outside_zone, meters)
    DomainError.Network -> stringResource(R.string.err_network)
    is DomainError.Unknown -> stringResource(R.string.err_generic_with_code, code)
}
ISS-03P1Money

Debt and balance disagree across screens, and with support

Same session, minutes apart.

What happens

Within a few minutes of one recording:

  • Home: "Balance actual: -$30.16. Alcanzaste el límite de saldo pendiente", which blocks cash orders.
  • Mis finanzas, Deuda total: $0.00.
  • Debt detail: -$397.90 for cash received and -$557.00 for a cancelled order.
  • Support bot: it had already removed the debt with an adjustment of $557.00 MXN.

Later that evening the queue still said "Menos pedidos por tu deuda". The next night the balance was +$8.69.

Impact on the courier

This is my money, and it decides whether I get cash orders, so it decides what I earn. Three numbers with no reconciliation break trust fast and push people to support.

Hypothesis

Each screen reads from a different source: the home card from a wallet or limits endpoint, Mis finanzas from a cut-off ledger aggregate, the detail from transaction rows. Caching differs per screen, nothing invalidates after a support adjustment, and no screen has an "adjustment pending" state.

How I'd fix it
High product · UX · process
  • One balance everywhere, "Saldo", with debt shown as a part of it.
  • "Ajuste en proceso" with an ETA right after a support adjustment.
  • Every banner that restricts orders links to the exact transactions behind it.
Medium architecture
  • A WalletRepository exposing StateFlow<Wallet> from one endpoint (or a BFF aggregate) that carries a ledgerVersion. Every screen observes it.
  • Invalidate on push: wallet.updated, support adjustment, order cancellation.
  • Track "conflicting balance shown" when home and ledger versions differ.
Low Kotlin
data class Wallet(
    val balance: Money, val debt: Money, val cashLimitReached: Boolean,
    val pending: List<Adjustment>, val ledgerVersion: Long,
)

class WalletRepository(
    private val api: WalletApi, private val dao: WalletDao,
    push: PushBus, scope: CoroutineScope,
) {
    val wallet: StateFlow<Wallet?> = dao.observe().stateIn(scope, SharingStarted.Eagerly, null)

    init {
        scope.launch { push.events.filter { it.type in WALLET_EVENTS }.collect { refresh() } }
    }

    suspend fun refresh() {
        val w = api.wallet()
        dao.upsertIfNewer(w)   // ignore responses older than the stored ledgerVersion
    }
}
ISS-04P1State

Offline and on a delivery at the same time, and auto-accept turns itself on

Two toolbars, two different truths.

What happens
  • Two toolbars stacked on home: "Estás desconectado" with its toggle, and right below it "En camino" with its own menu and help icons.
  • The connect screen showed auto-accept off. Right after connecting, home said "Autoaceptación activa".
  • Joining a virtual queue showed "Se encendió la Auto aceptación al entrar a la fila". It was switched on as a side effect.
Impact on the courier

Auto-accept assigns orders you didn't choose, and rejecting them hurts the acceptance rate that decides your tier. That's a consent problem and an earnings problem.

Hypothesis

Connection, order phase and preferences live in separate holders instead of one session state. The server enforces "queue implies auto-accept", but the toggle isn't driven by server state, so it shows a stale local value. The double toolbar looks like two fragments or NavHosts attached for different states, with the old one never removed.

How I'd fix it
High product · UX · process

Auto-accept is opt-in and never switches on silently. If a queue needs it, ask: "Para entrar a la fila se activará Auto aceptación. ¿Continuar?" Show the current state in one place, the top bar.

Medium architecture
  • One SessionState (connection × order phase × preferences) in a SessionStore, server-authoritative, with optimistic local intents.
  • Exactly one top bar rendered from that state.
  • If a policy overrides a preference, the response says so (autoAccept=true plus a reason) and the UI shows the reason.
Low Kotlin · Compose
data class SessionState(
    val connection: Connection = Connection.Offline,
    val phase: OrderPhase = OrderPhase.Idle,
    val autoAccept: Pref<Boolean> = Pref(false, source = Source.User),
)
data class Pref<T>(val value: T, val source: Source, val reason: String? = null)

fun reduce(s: SessionState, e: SessionEvent): SessionState = when (e) {
    is SessionEvent.ServerSnapshot -> s.copy(
        connection = e.connection, phase = e.phase,
        autoAccept = Pref(e.autoAccept,
            if (e.autoAcceptReason != null) Source.Policy else Source.User, e.autoAcceptReason))
    SessionEvent.WentOffline -> s.copy(connection = Connection.Offline) // phase kept: a delivery can be active offline
    else -> s
}

@Composable
fun SessionTopBar(s: SessionState) = when {
    s.phase is OrderPhase.Active && s.connection == Connection.Offline -> OfflineDuringDeliveryBar(s.phase) // one bar, not two
    s.connection == Connection.Offline -> OfflineBar()
    else -> PhaseBar(s.phase)
}
ISS-05P1Order flow · Money

Orders that dead-end, and orders that disappear without a word

Captured in about six minutes of recordings. Not published here because they show the customer chat.

What happens
  • At a convenience store, none of the 5 requested items were in stock. The customer wrote that the app wouldn't let them cancel; cancelling on my side meant a penalty; support told the customer to wait until the estimated delivery time passed. The screen stayed at "0/5 Seleccionados" with "Tengo los productos" disabled. Nothing in the app models this situation.
  • I reported it under "Situaciones con la tienda", where a photo is mandatory and the camera preview was almost black. After "Un momento por favor, estamos consultando el sistema" the app went back to 0/5, and about 10 seconds later jumped to "Buscando pedidos". No confirmation, no outcome, nothing about penalty or compensation.
  • Other captures: an order cancelled because the kitchen was slow, with me asking how to recover the money, and a "¿por qué no puedes finalizar el pedido?" menu.
Impact on the courier

Unpaid waiting, possible penalties and more support load. The worst part is not knowing how it ended.

Hypothesis

The order state machine has no state for "store can't fulfil" or "reported, under review". Reassignment arrives as a plain "order removed" event with no reason, so the client just navigates home. The report call is probably not idempotent, and the client probably doesn't wait for a ticket id.

How I'd fix it
High product · UX · process
  • First-class exits with a guaranteed outcome: "La tienda no tiene ningún producto" (no penalty, plus a waiting fee after N minutes), "Cocina demorada > X min", "El cliente pidió otra dirección".
  • Every report returns a visible ticket with status and outcome.
  • When an order is removed, a full-screen explanation: why, whether I'm paid anything, whether there's a penalty.
Medium architecture
  • Extend the state machine with Blocked(reason) and UnderReview(ticketId).
  • Send reports through WorkManager with an idempotency key, so a retry can't duplicate or race the reassignment.
  • Server pushes order.removed{reason, compensation, penalty}; the client renders it before going home.
  • CameraX with torch and exposure hints for the mandatory photo.
Low Kotlin
sealed interface OrderPhase {
    data object Idle : OrderPhase
    data class Picking(val id: String, val found: Int, val total: Int) : OrderPhase
    data class Blocked(val id: String, val reason: BlockReason) : OrderPhase
    data class UnderReview(val id: String, val ticketId: String) : OrderPhase
    data class Removed(val id: String, val reason: String, val compensation: Money?, val penalty: Boolean) : OrderPhase
}

class SubmitReportWorker(ctx: Context, p: WorkerParameters) : CoroutineWorker(ctx, p) {
    override suspend fun doWork(): Result {
        val key = inputData.getString("idempotencyKey")!!   // UUID created when the report is drafted
        return runCatching { api.submitReport(key, inputData.toReport()) }
            .fold({ Result.success(workDataOf("ticketId" to it.ticketId)) },
                  { if (runAttemptCount < 5) Result.retry() else Result.failure() })
    }
}

ISS-06P1Safety · Navigation

Navigation hand-off and chat aren't built for riding

Captured in screen recordings. Stills not published here.

What happens
  • Tapping "Navegar" opens a Maps-or-Waze chooser even though Maps was already selected. Google Maps then opens in car mode (22 min) and I switch to motorcycle mode (13 min) by hand.
  • With turn-by-turn running in picture-in-picture, I'm typing long free-text replies to a customer about a disagreement over the cash total.
  • "¡Vas tarde!" banners sit on top of the map, and one soft warning showed at 2:26 for an ETA window that ended at 2:23.
Impact on the courier

Extra taps and a slower route, since car mode was about 1.7 times slower here. Typing near or while riding is a safety issue.

Hypothesis

The navigation intent is built without a travel mode (mode=l selects two-wheeler in Google Maps) and the app preference isn't saved. Chat has no quick replies or structured actions like "Confirm total" or "Item unavailable".

How I'd fix it
High product · UX · process
  • Remember the navigation app and open it in one tap, in two-wheeler or bicycle mode to match the vehicle chosen at connect.
  • Quick replies in chat ("Voy en camino", "Llegué", "Producto agotado: ¿reemplazo?", "Confirma el total: $X") plus voice-to-text.
  • Show the cash total and payment method on the order card from acceptance onward. My captures don't show whether that exists today.
  • Shrink "¡Vas tarde!" to a compact chip while speed is above 10 km/h.
Medium architecture
  • Preferred navigation app in DataStore; vehicle mapped to Google Maps mode (d, b, l, w) and the Waze deep link.
  • Motion from the Activity Recognition API or fused-location speed. While moving: free text off, quick replies and voice on.
Low Kotlin · Compose
fun navIntent(dest: LatLng, app: NavApp, vehicle: Vehicle): Intent = when (app) {
    NavApp.GoogleMaps -> Intent(Intent.ACTION_VIEW,
        Uri.parse("google.navigation:q=${dest.latitude},${dest.longitude}&mode=${vehicle.gmapsMode}"))
        .setPackage("com.google.android.apps.maps")
    NavApp.Waze -> Intent(Intent.ACTION_VIEW,
        Uri.parse("https://waze.com/ul?ll=${dest.latitude},${dest.longitude}&navigate=yes"))
}
enum class Vehicle(val gmapsMode: String) { Motorcycle("l"), Bicycle("b"), Car("d"), Walk("w") }

ISS-10 · Errors that know what kind they are

Sub-lists load with a timeout so they can't sit on a skeleton forever, and the error kind drives the copy and the retry policy.

sealed interface UiState<out T> {
    data object Loading : UiState<Nothing>
    data class Data<T>(val value: T) : UiState<T>
    data class Error(val kind: Kind, val retry: () -> Unit) : UiState<Nothing> {
        enum class Kind { Offline, Timeout, Server }
    }
}

suspend fun <T> loadWithTimeout(ms: Long = 8_000, block: suspend () -> T): UiState<T> =
    runCatching { withTimeout(ms) { block() } }.fold(
        { UiState.Data(it) },
        { UiState.Error(if (it is TimeoutCancellationException) UiState.Error.Kind.Timeout else it.toKind()) { /* retry */ } })

Dark theme

A dark theme that still looks like Rappi

A lot of deliveries happen at night. A white screen at full brightness is tiring to glance at between turns, so I sketched a dark theme. Before picking colors I checked what the app actually uses, and found something worth sharing.

The brand finding

#FF441F
The commonly cited Rappi orange. I didn't find it as a solid fill anywhere in my captures.
#FE5B4A
Observed coral (connection toggle). The courier app's real brand accent is a slightly pinker coral.
#16625E
Observed teal on primary actions ("Lo tengo", "Continuar"). The CTA color is teal, not coral.
#007AFF
"Navegar" button. iOS blue, off-brand, and white text on it is 4.02:1.

Colors were picked with an eyedropper on JPEG screenshots and frames, so treat them as approximate.

Aceptar
3.08:1 · fails AA

White on the observed coral. White on #FF441F is 3.44:1, also a fail for body text.

Aceptar
6.2:1 · passes AA

Dark text (#1F0A05) on the proposed coral fill. Same brand, readable in sunlight.

So the proposal keeps the coral family as the brand accent and teal as the "go" color, which matches how the app already works: coral means brand and status, teal means confirm.

  1. No pure black. The background is a warm #161412 and elevation comes from lighter surfaces, not shadows. Pure black next to saturated coral smears on OLED screens.
  2. Coral changes by role. Text and icons use #FF8A75, CTA fills #FF5A47 with dark text, and large brand areas use primaryContainer. Full-saturation coral glows at night and pulls attention while riding.
  3. One coral fill per screen. It marks the money decision ("Aceptar"). Teal stays the confirm and progress color.
  4. Coral is not an error color. They sit close in hue, so errors always use error tokens plus an icon plus text. Never color alone.
  5. Money stays readable. Earnings in onSurface or success at 20sp or larger. Debt uses warning, not red, unless the account is blocked.
  6. Respect the sun. Default to "System" and offer "Auto at sunset". Dark mode outdoors at midday is harder to read, so don't force it.
  7. Gloves-sized targets. At least 48 dp, 56 dp for primary actions, and a 64 dp thumb on slide-to-confirm.

Plan

How I'd roll this out

Start with the fixes that are small in code and big for the courier, then move to the architecture that stops these bugs from coming back.

Week 1

Quick wins

  • Wrap the startup update check in a 3 s timeout and let the active order through.01
  • Add mode to the navigation intent and remember the chosen app.06
  • Render HTML and Markdown properly in chat and the bot.07
  • Stop showing raw server messages; map the known codes, generic copy for the rest.02
  • Seed the map camera from the last known location.09
  • Fix the typos, the "Opcional" badge, the time format and the red "Cancelar".111315
Weeks 2–6

Trust and consent

  • Auto-accept never turns on silently; ask before a queue enables it.04
  • Inset-aware bottom bars for every primary CTA, plus the QA matrix and screenshot tests.08
  • "Ajuste en proceso" state after support adjustments, and debt banners that link to their transactions.03
  • Disabled reasons and real error kinds in the help center.10
  • Notifications with sender and preview.16
This quarter

Architecture

  • Room-first active order and a startup path that never waits on the network.01
  • One WalletRepository with a ledgerVersion behind every money screen.03
  • One SessionStore reducer for connection, order phase and preferences.04
  • Order states for Blocked and UnderReview, idempotent reports through WorkManager, and removals that explain themselves.05
  • Error-code contract with the backend, risk-based verification and a post-delivery orchestrator.021215

Metrics I'd watch

Crash-free sessions

The baseline. Nothing else matters if the app falls over mid-delivery.

Cold start p90

Time to first interactive frame, with a separate cut for cold starts during an active order.

Stuck-on-launch rate

Share of cold starts where the splash stays up for more than a few seconds, measured with the startup-gate breadcrumbs from ISS-01.

Support contacts per 1k orders

Split by topic. Debt, dead-end orders and auto-accept should each go down on their own.

Debt-display mismatches

Sessions where screens show different ledgerVersion values. The client can detect it.

Closing

Why this matters to me

I've spent years stabilizing Android apps and the pipelines behind them, and these three weeks reminded me who the work is for. A courier waiting on a splash screen at a red light doesn't care about architecture. They care that the address is there. Most of what I found can be fixed with clear state, honest error messages and a few product decisions made explicit. I'd love to help build that.
