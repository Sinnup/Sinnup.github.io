Lo que falló en mis
turnos de Soy Rappi.

En octubre de 2026 hice entregas reales en la CDMX con la app de repartidores Soy Rappi. Soy ingeniero Android, así que cada vez que algo me estorbaba, lo grababa. Aquí está lo que encontré: 17 problemas, por qué creo que pasan y cómo ayudaría a resolverlos, desde la decisión de producto hasta el código en Kotlin.

Contexto

Por qué lo hice y cómo

Casi todas las revisiones de UX se hacen en un escritorio. Estas las hice en la calle, con un pedido en curso y un cliente esperando. Eso cambia lo que importa: dos segundos de más en la pantalla de inicio en tu casa son una molestia; en un semáforo, cuando necesitas la dirección de entrega, son un problema de verdad.

Quiero que la app sea mejor para la gente que la usa todos los días. Nada de esto busca exhibir a nadie. Cada problema viene con una propuesta que me encantaría construir.

01

Capturar en turnos reales

Capturas y grabaciones de pantalla tomadas en mi propio teléfono mientras trabajaba, del 7 al 28 de octubre. Sin cuentas de prueba ni flujos armados.

02

Catalogar con marcas de tiempo

Saqué un fotograma cada dos segundos de cada grabación y amarré cada hallazgo a una fuente y a un momento. Junté los hallazgos relacionados en 17 problemas.

03

Calificar por impacto en quien reparte

La severidad se mide por lo que le pasa al repartidor en la calle, no por qué tan feo se ve algo. Para cada problema escribí lo que vi, el impacto, una hipótesis de la causa y un arreglo en tres niveles.

Para que quede claro: no tengo acceso al código, los logs ni el backend de Rappi. Todo lo que describo como observado se ve en mis capturas. Las causas son hipótesis desde fuera y habría que confirmarlas con logs del cliente y trazas de red. Varios flujos los capturé una sola vez, así que no puedo decir qué tan seguido pasan. Los datos personales (nombres de repartidores y clientes, direcciones, números de pedido) están tapados con recuadros sólidos o pixelados, y dejé fuera por completo las pantallas con identificaciones o caras.

ISS-01P0Arranque

Atorado en "Verificando actualización" a media entrega

Unos 36 segundos de espera.

Qué pasa

En un arranque en frío, la pantalla de inicio muestra el logo, una línea de progreso delgada y "Verificando actualización", y nunca termina. Esperé unos 36 segundos, cerré la app desde Recientes, la volví a abrir y salió la misma pantalla. La app llegó a "En camino al cliente" hasta el minuto 1:25 de la grabación. Todo ese tiempo tenía una entrega en curso.

Impacto en el repartidor

Cerca de minuto y medio sin dirección, sin chat y sin botón de "Llegué", mientras el reloj de la hora estimada sigue corriendo. Eso puede terminar en una penalización por retraso, y significa detenerte en pleno tráfico a pelearte con el teléfono.

Hipótesis

Hay una compuerta de arranque que bloquea la navegación hasta que termina una llamada de red (la revisión de actualización in-app, o la de actualización forzada y remote config), y esa llamada no tiene timeout ni plan B. Con una conexión saturada, se queda colgada. Cerrar la app no sirve porque la compuerta se vuelve a ejecutar en cada arranque en frío. Lo más probable es que el pedido activo no se guarde localmente, así que no hay nada que mostrar antes de que responda la red.

Cómo lo arreglaría
Alto producto · UX · proceso

Nunca bloquear el acceso a un pedido activo. "Hay una actualización" pasa a ser un banner. Solo una versión que el servidor marque como crítica puede bloquear, y solo si no hay pedido activo. Medir el tiempo del arranque en frío al primer fotograma interactivo, con un número aparte para los arranques en frío durante un pedido activo.

Medio arquitectura
  • Guardar el pedido activo en Room a través de un OrderRepository y pintar primero desde la base de datos.
  • Hacer la revisión de actualización y de configuración en segundo plano, con un timeout estricto de 3 s.
  • Amarrar setKeepOnScreenCondition solo a que lo local esté listo.
  • Agregar breadcrumbs (startup_gate_start, startup_gate_timeout) a Crashlytics o Sentry.
Bajo Kotlin
class StartupViewModel(
    private val orders: OrderRepository,
    private val updates: UpdateChecker,
) : ViewModel() {
    val ready = MutableStateFlow(false)
    val updateBanner = MutableStateFlow<UpdateInfo?>(null)

    init {
        viewModelScope.launch {
            orders.activeOrderLocal().first()   // Room, no necesita red
            ready.value = true
        }
        viewModelScope.launch {
            val info = withTimeoutOrNull(3_000) { runCatching { updates.check() }.getOrNull() }
            when {
                info?.critical == true && orders.activeOrderLocal().first() == null -> navigateToForceUpdate()
                info != null -> updateBanner.value = info
            }
        }
    }
}
// Activity
installSplashScreen().setKeepOnScreenCondition { !vm.ready.value }
ISS-02P1Errores · i18n

Un error crudo del backend, en inglés, en la pantalla de la fila

Tres mensajes a la vez y ninguno me dice qué hacer.

Qué pasa

En la fila virtual de un restaurante ("Estás avanzando en la fila") se queda en pantalla un snackbar rojo: "The storekeeper is not trusted from any geo point." Al mismo tiempo, un aviso naranja dice que se activó la autoaceptación al entrar a la fila, y un banner dice "Menos pedidos por tu deuda".

Impacto en el repartidor

No supe si estaba en la fila, si me habían bloqueado en ese punto o si tenía que moverme. Es tiempo de espera sin ninguna respuesta. "Storekeeper" parece vocabulario interno para el rol del repartidor.

Hipótesis

El campo message del servidor se muestra tal cual, sin traducir el código de error a un texto localizado. Lo más seguro es que el backend comparó mi ubicación con la geocerca del punto y la rechazó. Es un estado legítimo; solo necesita un mensaje con el que pueda hacer algo, como "estás fuera de la zona de recolección, acércate".

Cómo lo arreglaría
Alto producto · UX · proceso
  • Una guía de redacción para errores: qué pasó, por qué y qué hacer ahora.
  • Cero texto crudo del servidor en builds de producción.
  • Un catálogo de textos a cargo de producto, con un linter de es-MX en CI que revise acentos y tono.
  • Los errores de geocerca muestran la distancia y una acción de "Muéstrame dónde".
Medio arquitectura
  • Los errores traen un code estable; el cliente lo convierte en un DomainError sellado.
  • Los códigos desconocidos caen en un mensaje genérico localizado y se registran con el payload original, que nunca se muestra.
  • Los textos que de verdad son dinámicos llegan con un locale y se traducen en el servidor.
Bajo Kotlin · Compose
sealed interface DomainError {
    data class OutsideGeofence(val meters: Int, val hub: LatLng) : DomainError
    data object Network : DomainError
    data class Unknown(val code: String) : DomainError
}

fun ApiError.toDomain(): DomainError = when (code) {
    "STOREKEEPER_UNTRUSTED_GEO" -> DomainError.OutsideGeofence(meta.distanceM, meta.hub)
    "NETWORK_TIMEOUT" -> DomainError.Network
    else -> DomainError.Unknown(code).also { Telemetry.unmappedError(code, rawMessage) }
}

@Composable
fun DomainError.message(): String = when (this) {
    // "Estás a %d m del punto. Acércate para entrar a la fila."
    is DomainError.OutsideGeofence -> stringResource(R.string.err_outside_zone, meters)
    DomainError.Network -> stringResource(R.string.err_network)
    is DomainError.Unknown -> stringResource(R.string.err_generic_with_code, code)
}
ISS-03P1Dinero

La deuda y el saldo no coinciden entre pantallas, ni con soporte

Misma sesión, minutos de diferencia.

Qué pasa

En unos cuantos minutos de una misma grabación:

  • Inicio: "Balance actual: -$30.16. Alcanzaste el límite de saldo pendiente", lo que bloquea los pedidos en efectivo.
  • Mis finanzas, Deuda total: $0.00.
  • Detalle de la deuda: -$397.90 por efectivo recibido y -$557.00 por un pedido cancelado.
  • Bot de soporte: ya había quitado la deuda con un ajuste de $557.00 MXN.

Esa misma noche, la fila seguía diciendo "Menos pedidos por tu deuda". A la noche siguiente el saldo era de +$8.69.

Impacto en el repartidor

Es mi dinero, y define si me llegan pedidos en efectivo, o sea, cuánto gano. Tres cifras que no cuadran acaban rápido con la confianza y mandan a la gente a soporte.

Hipótesis

Cada pantalla lee de una fuente distinta: la tarjeta de inicio de un endpoint de wallet o de límites, Mis finanzas de un agregado del ledger con fecha de corte, y el detalle de las filas de transacciones. Cada pantalla cachea a su manera, nada se invalida después de un ajuste de soporte y ninguna pantalla tiene un estado de "ajuste pendiente".

Cómo lo arreglaría
Alto producto · UX · proceso
  • Un solo saldo en todas partes, "Saldo", con la deuda como parte de él.
  • "Ajuste en proceso" con tiempo estimado justo después de un ajuste de soporte.
  • Cada banner que restringe pedidos enlaza a las transacciones exactas que lo causan.
Medio arquitectura
  • Un WalletRepository que expone un StateFlow<Wallet> desde un solo endpoint (o un agregado en un BFF) con un ledgerVersion. Todas las pantallas lo observan.
  • Invalidar con push: wallet.updated, ajuste de soporte, cancelación de pedido.
  • Registrar "saldo contradictorio mostrado" cuando las versiones del inicio y del ledger no coinciden.
Bajo Kotlin
data class Wallet(
    val balance: Money, val debt: Money, val cashLimitReached: Boolean,
    val pending: List<Adjustment>, val ledgerVersion: Long,
)

class WalletRepository(
    private val api: WalletApi, private val dao: WalletDao,
    push: PushBus, scope: CoroutineScope,
) {
    val wallet: StateFlow<Wallet?> = dao.observe().stateIn(scope, SharingStarted.Eagerly, null)

    init {
        scope.launch { push.events.filter { it.type in WALLET_EVENTS }.collect { refresh() } }
    }

    suspend fun refresh() {
        val w = api.wallet()
        dao.upsertIfNewer(w)   // ignora respuestas más viejas que el ledgerVersion guardado
    }
}
ISS-04P1Estado

Desconectado y en entrega al mismo tiempo, y la autoaceptación se prende sola

Dos barras, dos verdades distintas.

Qué pasa
  • Dos barras encimadas en el inicio: "Estás desconectado" con su switch, y justo abajo "En camino" con sus propios íconos de menú y ayuda.
  • La pantalla para conectarse mostraba la autoaceptación apagada. Justo después de conectarme, el inicio decía "Autoaceptación activa".
  • Al entrar a una fila virtual salió "Se encendió la Auto aceptación al entrar a la fila". Se prendió como efecto secundario.
Impacto en el repartidor

La autoaceptación te asigna pedidos que no elegiste, y rechazarlos baja la tasa de aceptación que define tu nivel. Es un problema de consentimiento y de ganancias.

Hipótesis

La conexión, la fase del pedido y las preferencias viven en lugares separados en vez de en un solo estado de sesión. El servidor impone "fila implica autoaceptación", pero el switch no se alimenta del estado del servidor, así que muestra un valor local viejo. La doble barra parece de dos fragments o NavHosts montados para estados distintos, y el viejo nunca se quita.

Cómo lo arreglaría
Alto producto · UX · proceso

La autoaceptación es opcional y nunca se prende sin avisar. Si una fila la necesita, se pregunta: "Para entrar a la fila se activará Auto aceptación. ¿Continuar?" El estado actual se muestra en un solo lugar, la barra superior.

Medio arquitectura
  • Un solo SessionState (conexión × fase del pedido × preferencias) en un SessionStore, con el servidor como fuente de verdad e intenciones locales optimistas.
  • Exactamente una barra superior, pintada desde ese estado.
  • Si una política se impone a una preferencia, la respuesta lo dice (autoAccept=true más un reason) y la interfaz muestra el motivo.
Bajo Kotlin · Compose
data class SessionState(
    val connection: Connection = Connection.Offline,
    val phase: OrderPhase = OrderPhase.Idle,
    val autoAccept: Pref<Boolean> = Pref(false, source = Source.User),
)
data class Pref<T>(val value: T, val source: Source, val reason: String? = null)

fun reduce(s: SessionState, e: SessionEvent): SessionState = when (e) {
    is SessionEvent.ServerSnapshot -> s.copy(
        connection = e.connection, phase = e.phase,
        autoAccept = Pref(e.autoAccept,
            if (e.autoAcceptReason != null) Source.Policy else Source.User, e.autoAcceptReason))
    SessionEvent.WentOffline -> s.copy(connection = Connection.Offline) // se conserva la fase: puede haber entrega activa sin conexión
    else -> s
}

@Composable
fun SessionTopBar(s: SessionState) = when {
    s.phase is OrderPhase.Active && s.connection == Connection.Offline -> OfflineDuringDeliveryBar(s.phase) // una barra, no dos
    s.connection == Connection.Offline -> OfflineBar()
    else -> PhaseBar(s.phase)
}
ISS-05P1Flujo del pedido · Dinero

Pedidos que se atoran, y pedidos que desaparecen sin decir nada

Capturado en unos seis minutos de grabaciones. No lo publico porque se ve el chat con el cliente.

Qué pasa
  • En una tienda de conveniencia no había ninguno de los 5 productos del pedido. El cliente me escribió que la app no lo dejaba cancelar; si yo cancelaba, me penalizaban; soporte le dijo al cliente que esperara a que pasara la hora estimada de entrega. La pantalla se quedó en "0/5 Seleccionados" con "Tengo los productos" deshabilitado. Nada en la app contempla esta situación.
  • Lo reporté en "Situaciones con la tienda", donde la foto es obligatoria y la vista previa de la cámara salía casi negra. Después de "Un momento por favor, estamos consultando el sistema", la app regresó a 0/5 y unos 10 segundos después saltó a "Buscando pedidos". Sin confirmación, sin resultado, nada sobre penalización o compensación.
  • Otras capturas: un pedido cancelado porque la cocina se tardó, conmigo preguntando cómo recuperar el dinero, y un menú de "¿por qué no puedes finalizar el pedido?".
Impacto en el repartidor

Espera que nadie paga, posibles penalizaciones y más carga para soporte. Lo peor es no saber cómo terminó.

Hipótesis

La máquina de estados del pedido no tiene un estado para "la tienda no puede surtir" ni para "reportado, en revisión". La reasignación llega como un simple evento de "pedido removido" sin reason, así que el cliente solo navega al inicio. La llamada del reporte probablemente no es idempotente, y el cliente probablemente no espera a recibir un id de ticket.

Cómo lo arreglaría
Alto producto · UX · proceso
  • Salidas de primera clase con un resultado garantizado: "La tienda no tiene ningún producto" (sin penalización, y con pago por espera después de N minutos), "Cocina demorada > X min", "El cliente pidió otra dirección".
  • Cada reporte regresa un ticket visible con su estado y su resultado.
  • Cuando se remueve un pedido, una pantalla completa que explique por qué, si me pagan algo y si hay penalización.
Medio arquitectura
  • Agregar a la máquina de estados Blocked(reason) y UnderReview(ticketId).
  • Mandar los reportes por WorkManager con una llave de idempotencia, para que un reintento no duplique ni se cruce con la reasignación.
  • El servidor manda order.removed{reason, compensation, penalty}; el cliente lo muestra antes de ir al inicio.
  • CameraX con linterna y ajustes de exposición para la foto obligatoria.
Bajo Kotlin
sealed interface OrderPhase {
    data object Idle : OrderPhase
    data class Picking(val id: String, val found: Int, val total: Int) : OrderPhase
    data class Blocked(val id: String, val reason: BlockReason) : OrderPhase
    data class UnderReview(val id: String, val ticketId: String) : OrderPhase
    data class Removed(val id: String, val reason: String, val compensation: Money?, val penalty: Boolean) : OrderPhase
}

class SubmitReportWorker(ctx: Context, p: WorkerParameters) : CoroutineWorker(ctx, p) {
    override suspend fun doWork(): Result {
        val key = inputData.getString("idempotencyKey")!!   // UUID creado al redactar el reporte
        return runCatching { api.submitReport(key, inputData.toReport()) }
            .fold({ Result.success(workDataOf("ticketId" to it.ticketId)) },
                  { if (runAttemptCount < 5) Result.retry() else Result.failure() })
    }
}

ISS-06P1Seguridad · Navegación

El paso a la navegación y el chat no están pensados para ir en moto

Capturado en grabaciones de pantalla. No publico fotogramas aquí.

Qué pasa
  • Al tocar "Navegar" se abre un selector de Maps o Waze aunque ya había elegido Maps. Después Google Maps abre en modo auto (22 min) y tengo que cambiar a modo moto (13 min) a mano.
  • Con la navegación paso a paso en picture-in-picture, estoy escribiendo respuestas largas a un cliente por un desacuerdo con el total en efectivo.
  • Los banners de "¡Vas tarde!" tapan el mapa, y un aviso apareció a las 2:26 para una ventana de entrega que terminaba a las 2:23.
Impacto en el repartidor

Toques de más y una ruta más lenta: aquí el modo auto era como 1.7 veces más lento. Escribir justo antes de arrancar o en movimiento es un tema de seguridad.

Hipótesis

El intent de navegación se arma sin modo de viaje (mode=l elige dos ruedas en Google Maps) y la app elegida no se guarda. El chat no tiene respuestas rápidas ni acciones estructuradas como "Confirmar total" o "Producto no disponible".

Cómo lo arreglaría
Alto producto · UX · proceso
  • Recordar la app de navegación y abrirla con un toque, en modo dos ruedas o bici según el vehículo que elegiste al conectarte.
  • Respuestas rápidas en el chat ("Voy en camino", "Llegué", "Producto agotado: ¿reemplazo?", "Confirma el total: $X") y dictado por voz.
  • Mostrar el total en efectivo y el método de pago en la tarjeta del pedido desde que lo aceptas. En mis capturas no se ve si eso ya existe.
  • Reducir "¡Vas tarde!" a un chip compacto cuando vas a más de 10 km/h.
Medio arquitectura
  • App de navegación preferida en DataStore; el vehículo se traduce al mode de Google Maps (d, b, l, w) y al deep link de Waze.
  • Movimiento con la Activity Recognition API o la velocidad de fused location. En movimiento: sin texto libre, con respuestas rápidas y voz.
Bajo Kotlin · Compose
fun navIntent(dest: LatLng, app: NavApp, vehicle: Vehicle): Intent = when (app) {

        .setPackage("com.google.android.apps.maps")
    NavApp.Waze -> Intent(Intent.ACTION_VIEW,
        Uri.parse("https://waze.com/ul?ll=${dest.latitude},${dest.longitude}&navigate=yes"))
}

Una encuesta de 12 pasos en pleno turno

Paso 2 de 12. La pastilla negra de arriba es Google Maps guiándome.

Qué pasa
  • El 23 de octubre, a la 1:33 p.m., la app me abrió una encuesta a pantalla completa con un contador de "1 de 12". El primer paso es tipo NPS: "Según tu experiencia de la última semana, ¿qué tan probable es que recomiendes ser Rappitendero a otra persona?", con una escala de 1 a 10 (sin el 0 que usa un NPS normal).
  • El paso 2 mete cinco calificaciones de 1 a 5 en una sola pantalla (ganancias en pedidos dobles, ganancias en lluvia, claridad de las ganancias, propinas y puntualidad del pago) y además un campo de comentario. Con eso ya van siete preguntas en dos pasos.
  • El contador dice que faltan 10 pasos. Solo capturé los dos primeros, así que no sé cuántas preguntas hay en total; si el resto se parece al paso 2, pueden ser varias decenas.
  • En la barra de estado se ve la navegación de Maps activa (1.1 km para la siguiente vuelta): la encuesta me salió yendo en ruta, no en un rato muerto. No pude confirmar qué la dispara, y en esas pantallas no veo forma de omitirla o dejarla para después.
  • En la misma pantalla están el "Continuar" debajo de la barra de navegación (ISS-08) y la falta "algùn" (ISS-13).
Impacto en el repartidor

Entre pedidos estás esperando la siguiente oferta o moviéndote a una zona con más pedidos, y cada minuto en un formulario largo compite con aceptar el siguiente. Una encuesta así se abandona: o se pierden los datos, o solo la terminan los más enojados, y las respuestas salen sesgadas justo en los temas de dinero que más importan. Si además sale con la navegación activa, es una distracción más en la calle (ISS-06), y se suma a las interrupciones después de cada entrega (ISS-15).

Hipótesis

Parece un solo formulario armado en bloque y lanzado igual a todos, sin tomar en cuenta el momento ni el contexto del repartidor. Lo más probable es que las respuestas se manden hasta el final, así que si alguien abandona en el paso 5 se pierde todo lo que ya contestó, y nadie sabe en qué paso se cae la gente.

Cómo lo arreglaría
Alto producto · UX · proceso
  • Partir la encuesta en microencuestas de 1 a 3 preguntas, repartidas en días o semanas y disparadas cuando la pregunta tiene sentido: sobre propinas justo después de un pedido con propina, sobre las ganancias en lluvia un día que llovió, sobre pedidos dobles después de uno doble.
  • Siempre con "Ahora no" a la vista, y nunca con un pedido activo o la navegación abierta.
  • Muestreo: no todos responden todo. Cada pregunta le toca a una muestra de repartidores, y con eso alcanza para tener datos confiables.
  • Progreso honesto: "2 preguntas, unos 20 segundos" en vez de un contador que revela la sorpresa en el paso 1.
Medio arquitectura
  • Configuración de encuestas desde el servidor: un banco de preguntas con reglas de disparo (evento más contexto), muestreo y rotación por repartidor.
  • Tope de frecuencia en el cliente y en el servidor, por ejemplo una microencuesta cada 3 días como máximo.
  • Cada respuesta se guarda en cuanto se contesta (Room más WorkManager), no al final, así que una encuesta abandonada a medias igual deja datos.
  • Analítica de abandono por paso y por pregunta, para saber dónde se cae la gente y qué preguntas sobran.

data class SurveyContext(
    val event: CourierEvent,          // p. ej. OrderDelivered(tipped = true), RainShiftEnded
    val hasActiveOrder: Boolean,
    val isNavigating: Boolean,
)

class SurveyScheduler(
    private val pool: QuestionPool,   // viene del servidor, con reglas de disparo y muestreo
    private val history: SurveyHistoryDao,
    private val courierId: String,
    private val clock: Clock,
) {
    suspend fun pick(ctx: SurveyContext): List<Question> {
        if (ctx.hasActiveOrder || ctx.isNavigating) return emptyList()   // nunca en ruta
        val last = history.lastShownAt()
        if (last != null && Duration.between(last, clock.instant()) < MIN_GAP) return emptyList()
        return pool.questions
            .filter { it.trigger.matches(ctx.event) && it.isSampledFor(courierId) && !history.answered(it.id) }
            .sortedBy { it.priority }
            .take(MAX_QUESTIONS)
    }

    companion object {
        val MIN_GAP: Duration = Duration.ofDays(3)
        const val MAX_QUESTIONS = 3
    }
}

// Cada respuesta se guarda al momento: si el repartidor se sale a medias, no se pierde nada.
fun onAnswer(q: Question, value: Int) = viewModelScope.launch {
    answers.insert(Answer(q.id, value, clock.instant()))
    SyncAnswersWorker.enqueue(appContext)
}

Sesiones sin crashes

La base. Nada más importa si la app se cae a media entrega.

Abandono por pregunta

Llevo años estabilizando apps Android y los pipelines que las sostienen, y estas tres semanas me recordaron para quién es ese trabajo. Casi todo lo que encontré se arregla con un estado claro, mensajes de error honestos y unas cuantas decisiones de producto puestas por escrito. Me encantaría ayudar a construirlo.
